# 物理链（「物理视角」页）的规则与口径

这份文件是**口径的账本**：本页的规矩都记在这里，改代码/改真源之前先读它。数据在 `chain.json`（真源，逐字转录自 PDF）、代码论文清单在 `papers.md`。

## 一、表面只有一条链（公式与物理），代码实现沉到子图（**推翻**早先"两条流并排"的写法）

- **表面是一条链，全部用物理语言**：量决定量（`f*、ζ、T_vir^min、L_X` → `ρ̇*` → `Ṅ_ion / ε_heat` → `x_HI / T_K` → `J_α → x_α` → `T_S` → `δT_b` → `P_21(k,z)`；旁支 `φ(M_1500)`、`τ_e`）。
- **"未在代码里定位到"这句话有门槛**（判据）：只许在**搜够了**之后写。判据：① 全仓搜（不只一个文件）；② 换同义词与相关量名（`x_c` 要找 `xc_inverse`、`1/x_c`、`kappa_10` 这类）；③ **写明搜过什么**（在哪个文件、试过哪些名字）。**"我没找到"≠"代码里没有"**——先如实写"我搜了 X、Y、Z 没命中"，再往下查，别把没搜到写成没有。
  - 反例：`x_c` 曾被我写成「未在代码里定位到」，实际就在 `SpinTemperatureBox.c:1074`（叫 `xc_inverse`）——只是我当年只搜了一个文件、只试了四个名字。
  - **真正"代码里没有"的**才写"**代码不产出**"，而且要有正面证据（例如 `P_21`：产物清单 P01–P17 里没有功率谱，核心只输出盒子与光锥）。
- **理论推导与代码实现"完全两码事"的量：图上按代码画，理论写进文档**。判据：某个量的理论式（PDF 里那个式子）与代码实际执行的算法**不是同一套**——不是"一行 vs 一串"的粒度差，而是**算法本身就不同**。这时：**图上以代码为准**（节点与边照代码的实际步骤画），**理论在文档里给**（记明对应 PDF 的哪一节 / 哪一 Eq，并注明"代码用的是另一套算法"）。
  - 已确认属于这一类（自查，2026-09-29）：`Q_HII / x_HI`（理论是 Eq.3 的一阶 ODE；代码是游程集 / 逐格点判据，**不求那个 ODE**）、`T_S`（理论是 Eq.5 的三个温度调和平均；代码是沿视线分**径向环**积分）、`x_c`（理论是碰撞率之比；代码路径**尚未定位到**）。更彻底的是 `P_21`——代码根本不产出它（分析层）。
- **代码怎么算出来的，属于子图**：公式里是一个积分、代码里是"离散晕累加 + 积分器 / 条件表"，那么**表面只放那个积分式（父模块）**，离散累加、积分器、滤波、网格装配都是它的**子节点**（默认收起）。
- **判据一句话：表面是"算什么"，子图是"怎么算"。禁止把代码和公式并排放在同一层**——并排放会让同一个物理出现两个并列入口，读者无从判断哪个才是"这个量本身"。
- ⚠️ **本条的待改**（据本条规则，数据要动，尚未动手）：① 把 `source_grid`（S12.2 晕源项网格——离散晕累加，属"怎么算"）从表面移进子图，父模块是 Eq.1 / Eq.4 的积分式；② 节点符号 `S12.1` / `S12.2` 是 atlas 阶段编号（文档形状），要换成物理写法；③ `PHOTON_CONS_TYPE`、`USE_MINI_HALOS` 的挂点改回**表面边** `rho_star->nion`（它们的代码细节进子图）。
- **有实现选择的环节：表面只放"公式或物理过程的名字"，选择项与各自后续流程进子图**。例：表面是"宇宙学背景"这个过程/公式，点开子图才看到传输函数有哪几种可选、每种之后接什么；表面是"质量函数"的公式，子图里才是 PS / ST / WATSON / DELOS 各自的流程。**表面上不留选择项**，也不因"有选项"画虚线。⇒ 这条**更新**了第八节第 7 条表里"实现选择 → 挂模块标签"的写法：改为**进子图**。
- **虚线框只剩一个用途**：这个流程/模块在某些配置下**根本不存在**（并写明由哪个参数决定）——见第八节第 7 条末。
- **物理层里多种"种类"并存，用颜色区分**：**物理量**（`T_S`、`x_HI`、`M_min`）、**谱**（`P_21`、物质功率谱 `P(k)`）、**函数 / 关系**（晕质量函数 `dn/dM`、光度函数 `φ(M_1500)`、标度关系）**都是物理层的东西，允许同图并存**——它们不是同一类，但**用颜色区别种类**就够了，不因此分层、不因此另开页面。**观测量**（根）单独一色，**子图**节点用暗色。
  - 连带结论（回答"功率谱、质量函数要不要立表面节点"）：**要**。它们是物理层的"谱 / 函数"，各自可以有子图（如 `dn/dM` 的子图里放 `HMF` 用哪种、`P(k)` 的子图里放 `POWER_SPECTRUM` 用哪种）。
- **子图不只有工程**："表面只放物理、工程进子图"约束的是**表面这一层**；**子图里放什么由可读性决定——可以是更细的物理，也可以是实现细节**。它服务的是**自顶向下地读**与画布可读性，**不是**"物理 / 工程"的分界线。
  - 因此节点有**两个互不干扰的属性**：**层级**（`layer`：表面 / 子图）与**种类**（`kind`：物理量 / 谱 / 函数 / 过程 / 工程项）。一个物理节点的子图里，完全可以再放物理。
- **怎么判断"概括模块"还是"某个过程的子过程"**（判据如下，**不看代码体量**）：
  1. **推导里有没有它自己的名字 / 方程号？** 有（Eq.1 的 `dn/dM`、Eq.2 的 `M_min`、Eq.9 的 `δT_b`）→ 表面；只在代码里存在 → 子图。
  2. **它被几处下游用？** 被多处共享（`dn/dM` 同时供源项与晕目录）→ 概括度高 → 表面；只服务一处 → 子过程。
  3. **它在时间上独立成立吗？** 是随红移独立成立的函数 / 场（`dn/dM(M,z)`）→ 表面；只是某一步的中间量（快照常数、累加缓冲、滤波中间件）→ 子图。
  4. **换掉它，改变的是"整个环节走哪条路"还是"某一步怎么算"？** 前者（`SOURCE_MODEL`、`HMF`、`POWER_SPECTRUM`）→ 那个环节**在表面要有名字**，选择本身进子图；后者（积分器、滤波核）→ 子图。
  - **反例提醒（最容易搞错的地方）**：`mmin` 在代码里只有一行幂律、很小，但它是 Eq.2 的独立物理量 → **表面**；`HaloBox.c` 是个大文件，物理上只是"把 Eq.1 的积分算出来" → **子图**。⇒ 判据是"物理上独立"而不是"代码上大"。
  - **拿不准时的兜底**：问一句"科学家会单独问『这一步是什么』吗？"——会 → 表面；不会（"累加到网格怎么做"）→ 子图。
- **一张图里不许物理与工程夹杂**（**最严的一条**）：表面上**一个工程项都不许有**，哪怕只有一个最不起眼的（比如"整文件扫描"这类实现动作）。只要出现不属于本层的东西，就用同一套办法处理：**挂一个本层语言的名字当父节点，把那个东西放进它下面的子图**（默认收起）。层次判据：**这一项是不是一个物理过程 / 物理量 / 物理参数？** 是 → 本层；不是 → 父节点 + 子图。
  - **附带结论**：物理页面里**不设"工程与装配"这类收起的区块**——那等于把工程搬进这张图。工程的地盘是画布页；两张图各自纯粹，需要时用「看实现」这类出口跳过去，而不是在本层里塞一个工程区。
- 参数与这条链的**接缝**：
  - **驱动量**挂在公式流的两端（决定"算什么"）；
  - **效应开关**（`USE_*`、`PHOTON_CONS_TYPE`…）挂在**边**上——画成**虚线箭头 + 箭头上的虚线框**（沿用仓库"虚线 = 条件/可选"的既有语义）。
  - **实现选择**（`INTEGRATION_METHOD_*`、`HMF`、`POWER_SPECTRUM`、`SOURCE_MODEL`…）挂在**模块**上，标明"可选的实现"。
  - **数值与精度**（`R_MAX_TS`、`N_STEP_TS`、`K_TARGET`…）**暂不纳入**。
  - ⚠️ 这三类的判据以**第八节第 7 条**为准：这一段原先把三类混写成"数值参数 + 效应开关"，2026-09-29 校正。

## 二、表面只放"贴近物理的环节"，细碎的进子图

1. **理想情况**：某个物理量在代码里就是**一处干净的封装**（公式一行 ↔ 代码一处）⇒ 图上**直接一一对应**，不额外展开。
2. **否则**（公式一行、代码一串）⇒ **按代码的流程展开**，但**只展开到"仍然是一个物理环节"为止**：
   - 例：`ρ̇* → Ṅ_ion` 这条粗边，按代码拆成 **S12.1 恒星标度关系**（晕质量 → 恒星质量份额/形成率/金属性/X 射线）与 **S12.2 晕源项网格**（`ComputeHaloBox` / `sum_halos_onto_grid`）——这两步**本身就是物理**，放表面。
3. **更细的（软件工程 / 数值算法）不上表面**：FFT 与滤波实现、`mean_fix_grids` 这类网格装配、条件表插值、缓存、断点续算、MPI/OpenMP 并行——**等有兴趣再生成子图**（默认收起）。
   - **判据一句话**：这一环节本身是不是一个物理过程或物理量？是 → 表面；不是 → 子图。

## 三、防漏的硬规矩（自检来守）

- 每个公式量/边 **必须有至少一条"算法锚点"**（求值方式 / 所处循环层级（初始化一次·每红移一次·红移循环内子步） / 受哪些离散化参数控制 / 代码落点），**或者显式标注「未在代码里定位到」**——不许静默留空。
- 效应开关门控的箭头必须真实存在（否则那条虚线无处可挂）。
- 公式 MUST 逐字等于真源；生成器不许改写。

## 四、不做（边界）

- **不做评估层**：不加批注/评估字段（评估是使用者自己的事）。
- **不凭印象补文献或参数含义**：来源论文只在代码注释里真实写着时才填；缺就留空，并在自检日志里报数量。
- **算法流里的纯工程细节不进这一页**（缓存、持久化、并行、断点续算、HDF5 落盘 → 属画布 S02/S03/S16 的管辖）。
- **不加单位/量纲**：图上只给符号、公式与出处，不做量纲标注。

## 五、命名政策

- 图上**物理量按 P&L 2012 的写法**显示（`f*`、`ζ`、`T_vir^min`、`x_HI`、`T_K`、`T_S`、`δT_b`、`P_21`、`τ_e`）；**不追代码变量名**。
- 同一个量的不同名字，以 P&L 的写法为准；代码名只作附注字段（自检断言：节点符号不许是代码常量名）。
- **名字里不带代码坐标**：框上的块名与步骤名、骨架文档的文件名与标题都只写名字（`气体热与自旋温度`、`解自旋温度`、`thermal.md`）。阶段号与模块码（`S14.3.1`、`M8`）是**代码坐标**，只活在数据里（`stage` / `stages` / `stepId` / 源码引用的 `label` / `codeHints`）与检索命中面上——按 `S14` 检索照旧能查到，但界面上一个都不印（自检的「呈现面」一节守这一条：标签 / 落点 / 散文 / 骨架 / 命中说明五类出口都在生成物与真源上重算）。

## 七、口径细节（节点 / 边 / 落点）

1. **表面新增的两个物理环节节点**：`scaling_relations`（S12.1 恒星标度关系，名与描述取自 atlas L4·S12.1.1 / S12.1.2 原文）与 `source_grid`（S12.2 晕源项网格，取自 L4·S12.2.1 原文）。`fstar->rho_star` 与 `mmin->rho_star` 两条粗边改为经 `scaling_relations` 走，另加 `scaling_relations->source_grid`、`source_grid->nion`；**公式流的 `rho_star->nion`（Eq.4）刻意保留**——它与 `source_grid->nion` 是同一关系的两种表示（体积平均 vs 3D 网格），并列摆出才看得出两条流的接缝。
2. **开关挂在哪条边上**：`USE_UPPER_STELLAR_TURNOVER → fstar->scaling_relations`、`USE_MINI_HALOS → scaling_relations->source_grid / source_grid->nion`、`PHOTON_CONS_TYPE → source_grid->nion`；改挂理由记在各条 `gatesEdges` 的 `basis` 里。
3. **实现步骤层已落地**：块的成员各是一个 `step:*` 节点（21 个），贴在块的**成员层**里——一级上只讲 12 个块，走进那个块才看得到成员，引用由这些叶子决定（见 §九）。
4. **子节点数的口径**：
   「进入子图 ↗」旁边那个数字只数**这个对象自己的**子对象——**块＝它自己的成员数**（`kind: layer` 的层为 0，入口不出现）、**成员＝它自己的实现步骤数**（没有步骤即 0，入口不出现）。"这个量装在哪个块里"是另一件事（归属反查）：
   拿它当成员自己的子节点数，⑨观测量 里的 `P_21` / `k_target`（没有实现步骤）会报出 ⑨观测量 的成员数「4 个子节点」，点进去却是一张空画布。数字与"能不能进"共用 lib 的 `subgraphSizeOf` 一处判据，自检真跑它（过程块 / 层 / 有步骤的成员 / 无步骤的成员各钉一个值）。
5. **开放项**：`algorithm` 段尚未写全——已写 2 条，其余 4 项以 `algorithmPending` 显式标注「未写 / 未在代码里定位到」，不许静默留空（第三节的硬规矩）。

**落点精度**：`codeHints` 现在支持**子过程级**（如 `S12.1`）——生成器把每个落点同时挂在阶段键与子过程键下，所以两个新节点的「看实现」落在对的那几个函数上，而不是该阶段的前 8 个（`build-physics-chain.mjs`）。

## 八、参数分流：宇宙学挂标签，天体物理进抽屉

1. **宇宙学与物质背景的参数分两类处理**：
   - **控制性**（决定走哪条路的选项）：**作为标签挂在模块上**，被挂的模块画成**虚线框**（沿用仓库"虚线 = 条件/可选"的既有语义）。已核实归属：这类选项在 `MatterOptions`（`wrapper/inputs.py:560`）——`HMF`、`POWER_SPECTRUM`、`PERTURB_ALGORITHM`、`SOURCE_MODEL`、`SAMPLE_METHOD`、`FILTER` / `HALO_FILTER`、`FDM`、`HMF_FINDEX`、`USE_RELATIVE_VELOCITIES`、`USE_INTERPOLATION_TABLES`、`KEEP_3D_VELOCITIES` 等，**不在** `CosmoParams` 里。
   - **硬编码常量**（源码里写死的数，如 `Constants.c:25` 的 `T_cmb = 2.7255`）：**只写进文档，不上图**——不替这类常量建节点，也不去关心它们。
2. **天体物理参数是最重要的一层**：要能**当词条检索到它作用的流程**。它与宇宙学参数**分开处理**，单独做一个「天体物理参数」抽屉：选中某个参数词条 → **高亮它相关的模块**（不另开页面）。
3. 因此参数在数据里是**两条通道**，视图上也是**两套入口**：宇宙学（标签 + 虚线框）与天体物理（抽屉 + 高亮）。
4. **开关写箭头上**：`AstroOptions` 的开关（`USE_*`、`INTEGRATION_METHOD_*`、`PHOTON_CONS_TYPE` 等）继续画在它门控的那条**边**上（虚线箭头 + 箭头上的虚线框），**不**改成挂模块的标签——它描述的是"这条依赖要不要走"，不是"这个模块存不存在"。
5. **参数按"在物理里起什么作用"分流，不按"是不是用户输入"分流**（⚠️ **下表按"代码类"划的两行——"宇宙学控制性选项"与"天体物理开关"——已按第 7 条作废**，）：

| 类别 | 例子（带归属类） | 处理 |
| --- | --- | --- |
| 天体物理数值参数 | `F_STAR10`、`F_ESC10`、`M_TURN`、`L_X_MINI`、`A_LW`…（`AstroParams`，58 个） | 抽屉词条，可检索，选中高亮相关模块 |
| 天体物理开关 | `USE_MINI_HALOS`、`USE_TS_FLUCT`、`INTEGRATION_METHOD_*`（`AstroOptions`，17 个） | 写箭头上（见第 4 条） |
| 宇宙学控制性选项 | `HMF`、`POWER_SPECTRUM`、`SOURCE_MODEL`、`PERTURB_ALGORITHM`…（`MatterOptions`） | 挂模块标签，被挂模块画虚线框 |
| 宇宙学数值参数 | `hlittle`、`OMm`、`OMb`、`POWER_INDEX`、`Y_He`…（`CosmoParams`，11 个） | **当常量处理：只写出来（列进数据/文档）即可，不上图、不深挖**。不替它们建节点、不追它们进哪条公式 |
| 数值与精度参数 | `R_MAX_TS`、`N_STEP_TS`、`PHOTONCONS_CALIBRATION_END`（现有 `numeric` 组）＋ `HII_DIM`、`BOX_LEN`、`N_THREADS`、采样器参数（`SimulationOptions`，待逐条核实） | 归「数值与精度」一组：可检索，并标明"只改离散化与代价、不改物理" |
| 硬编码常量 | `Constants.c` 的 `T_cmb = 2.7255` 等 | 只写文档，不上图 |
| 代码内部派生量 | `_BOX_LEN`、`_DIM`、`_SIGMA_8` ↔ `A_s`、`_base_cosmo` | 不列成条目；在相关词条里注明"由…推得" |

6. **"用户参数"不是一类物理角色**：用户能设的（模板 / YAML / 代码默认）与代码里那四个结构体是**同一批参数**；"从哪来、能不能被覆盖"作为**词条上的来源字段**记录，不上图。
8. **两处收口**：
   - `k`（`K_TARGET`）**不进参数表**：它是分析时自选的波数，不是模型参数。图上仍保留它作为"看哪一段"的入口，但标明"**非模型参数**"。

7. **按代码类分流是错的，改按逻辑分流**（2026-09-29 校正）：
   - `MatterOptions`（宇宙学/物质侧）与 `AstroOptions`（天体物理侧）的分界是**按配置对象**，**不是按逻辑**——两边都有"效应开关 / 实现选择 / 数值开关"三类：`USE_RELATIVE_VELOCITIES`、`FDM` 是宇宙学侧的**效应开关**；`INTEGRATION_METHOD_*`、`HMF`、`POWER_SPECTRUM`、`SOURCE_MODEL` 是天体物理/物质侧的**实现选择**，不是开关。所以第 5 节表里"宇宙学控制性选项"与"天体物理开关"两行**按类划的写法作废**，按下面这张表划：
   - **逻辑上只有三类**（据此决定画在哪）：

   | 逻辑类别 | 判据 | 例子 | 画在哪 |
   | --- | --- | --- | --- |
   | 效应开关 | 加/减一条**物理项或依赖** | `USE_X_RAY_HEATING`、`USE_MINI_HALOS`、`USE_TS_FLUCT`、`USE_RELATIVE_VELOCITIES`、`FDM` | **箭头上**（虚线箭头 + 箭头上的虚线框） |
   | 实现选择 | 在几种公式/算法里**选一个**，模块本身总在 | `HMF`、`POWER_SPECTRUM`、`SOURCE_MODEL`、`INTEGRATION_METHOD_*` | 挂**模块**标签，写明"可选的实现"；模块**不**画虚线框 |

   - **虚线框的语义**：虚线框 = **这个模块/流程是非必要的**（有些配置下根本不存在），**不是**"这个参数可选"。因此只用在**某个选择会让整段流程消失**的地方——按现有读点最像的是 `PHOTON_CONS_TYPE = no-photoncons` 时那条光子守恒校准流程不参与（`IonisationBox.c:1373`、`scaling_relations.c:70-127`），**待用代码确认后再画**。

## 九、引用口径：叶子最细、祖先 = 并集、模块 = 成员的并集

**一句话**：每个对象的引用由**最深一层的落点**唯一决定，上级**不自造**引用。

1. **叶子是最细的落点**：21 个实现步骤（`step:*`，图上最深、没有子节点）写自己的落点——代码引用是生成器按单元收的那几条，笔记引用指向它所属模块骨架文档里的一个小节。
2. **祖先 = 自身的 ∪ 全部直接子节点的**：`refs(节点) = 去重排序(自身的 refs ∪ ⋃ 直接子节点的 refs)`（子节点按 `parent` 反向表算）。
3. **模块 = 成员的并集**：`refs(块) = 去重排序(块自身那几条 ∪ ⋃ 成员的 refs)`。块**不看 `parent`**，成员只认真源 `blocks.items[].members`（归属的唯一来源）。
4. **L1 共享内核层直接给出，不靠汇总**：它的 16 个成员是头文件名、不是图上节点，汇总不到——那 16 条**文件级**代码落点（`codeAnchor.kind === 'files'`，行区间 = 1 到文件末尾）与 1 条笔记引用写在真源里，生成器照抄。
5. **去重键与排序**（生成器与自检**各实现一遍**再逐条对拍）：

   | 类别 | 去重键 | 排序 |
   | --- | --- | --- |
   | 代码引用 | `file:line:endLine` | 文件路径 → 行号 → 结束行，**逐字符**比较 |
   | 笔记引用 | `docId#anchor` | 文档路径 → 锚点，**逐字符**比较 |

   去重键**不含 `label`**（同一条落点会同时挂在父与子、两边标签不同，带上就永远去不掉重）；排序**不用 `localeCompare`**（它会随运行环境的 ICU 变，产物会抖）。代码引用整体排在笔记引用前面。
6. **视图只读、不自己汇总**：物理链页读生成物给的 `refs`；`Inspector` 的两个入口按 `file` 是否为空把它分成「看实现」与「看文献」，数量标号 = 对应清单的长度。自检从叶子**独立重算**一遍再逐条对拍，多一条、少一条都失败并指名对象与那一条。
7. **反面**：块属性页**不再**出现「代码锚」「阶段号」这类点不开的摘要（字段仍在生成物里、自检仍逐条断言；"这块 / 这个量算在哪段代码里"由「看实现」的落点回答）。

### 骨架文档（位置与补写方式）

- **位置**：`docs/notes/physics-chain/modules/*.md`，共 12 份 —— 10 个过程块 + 「常数与网格层」+ 「共享内核层」各一份。**文件名＝块 id 去 `block:` 前缀**（`block:thermal` → `thermal.md`），标题＝块名，不带模块码。
- **形状**：标题（H1，即块标签）+ 逐成员 `##` 小节 + 逐步骤 `###` 小节。小节标题的 slug 就是引用里的 `anchor`（口径同 `Graphify/src/lib/slug.ts`），所以**改小节标题等于改锚点**，两处必须一起改（自检会查每条笔记引用的锚点能否在该文档里定位到小节）。
- **补写正文**：直接往小节里写；**不用改页面代码**，也不必因补写而调整引用。
- **引用怎么来的**：`docId` 是**相对 `docs/notes/` 的 POSIX 路径**（如 `physics-chain/modules/thermal.md`），服务端按目录扫描即可打开，**无需另行登记**。
