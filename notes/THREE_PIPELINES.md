 

# 三条时间流水线：E1 联合演化盒 / E2 光锥 / E3 全局演化

> **这份文档讲什么**：21cmFAST 对外只有三条"跑一次仿真"的路（联合演化盒、光锥、全局演化）。本文把这三条路**自顶向下拆开**——先立整条链的框架，再逐环交代它在算什么、为什么需要它、交出什么量，最后才谈它怎么工作。代码层面只讲**结构与数据流**（谁在什么顺序上做什么、把什么交给谁），不逐函数展开。
> **每个小节的标题正下方第一行，就是这一节的「代码位置」**：只写"落在哪个文件的哪个符号"——**仓库根相对路径 + 符号名，不给行号**（行号会随代码变动而失效）。它只负责指位置，不解释实现；想读代码时直接从这一行跳。§0–§5 这六个章节标题本身不重复给（它们的位置由各自小节承担）。
> **本文不写**：公式与推导、函数级的实现细节、缓存与内存策略、断点续算与并行、边界与退化情形（单格、无离散晕、关掉某个物理开关等）。这些都是"实现细节"层，与"这条链在干什么"无关。
> **读法**：§0 是框架（先读它）；§1 是每一环的"上户口"（位置、动机、产物）；§2 是三条路共用的骨架；§3–§5 才逐条拆开；§6 并排对照。**任何名词在 §0–§1 里都先交代过它是什么、在哪一环出现、被谁消费**，后面的小节才允许直接使用。

## §0 先把框架立起来

### 0.1 一句话

> **代码位置**：Python 编排在 `src/py21cmfast/drivers/`，C 计算在 `src/py21cmfast/src/`；对外入口都从 `src/py21cmfast/__init__.py` 再导出。

这个码要算的是：**宇宙从一团几乎均匀的初始物质，怎么一步步长出星系、把它们之间的氢气电离掉，并在这个过程中产生可观测的 21cm 信号。**

它不模拟流体与辐射的相互作用细节，而是用一套**解析配方**回答"物质在哪里成团、成团处产生多少光"，再把结果放到三维网格上按红移逐步推进。

### 0.2 一条主链，六个环节

> **代码位置**：①`src/py21cmfast/wrapper/inputs.py`（`InputParameters` 及各子结构）②③`src/py21cmfast/src/InitialConditions.c`、`src/py21cmfast/src/PerturbedField.c` ④`src/py21cmfast/src/HaloCatalog.c`、`src/py21cmfast/src/Stochasticity.c` ⑤`src/py21cmfast/src/HaloBox.c` ⑥`src/py21cmfast/src/IonisationBox.c`、`src/py21cmfast/src/SpinTemperatureBox.c` ⑦`src/py21cmfast/src/BrightnessTemperatureBox.c`。

下面这张表是**全文的坐标系**。任何术语都可以在这里找到它的位置：它属于哪一环、为什么必须有、交出什么给下一环。

| 环节        | 它回答的问题                                   | 为什么必须有它                                                 | 交出什么                                                                                   |
| :---------- | :--------------------------------------------- | :------------------------------------------------------------- | :----------------------------------------------------------------------------------------- |
| ① 参数     | "这次模拟的宇宙长什么样、算多细"               | 所有后续计算都要读它                                           | 一套自洽的物理与数值设定                                                                   |
| ② 初始条件 | "最开始的扰动长什么样"                         | 后面所有结构都是从这一个随机场长出来的                         | 一张**密度场**（哪里比平均密、哪里比平均稀）与它派生的**位移场**（物质往哪走） |
| ③ 微扰场   | "到了某个时刻，这些扰动长到多大了"             | 不同时刻的宇宙不同，必须把初始场"推到"目标时刻                 | 该时刻的**密度场**与该时刻的**速度场**                                         |
| ④ 晕       | "哪些地方已经塌缩成团了、有多重"               | 星系只住在塌缩成团的暗物质结构里，辐射的来源在它们那里         | **晕目录**（一批晕，各有质量与位置）                                                 |
| ⑤ 源项     | "每个格子上产生了多少辐射"                     | 电离与加热的方程是逐格写的，需要"逐格的辐射量"而不是"哪里有晕" | **源项网格**：每格的**电离光子数**、**恒星形成率**、**X 射线**     |
| ⑥ 电离与热 | "每个格子的氢气被电离了多少、气体热到什么程度" | 这是 21cm 信号的两个直接决定因素                               | **电离盒**（还剩多少中性氢）+ **自旋温度盒**（气体温度与自旋温度）             |
| ⑦ 亮温     | "最后观测到的信号是多少"                       | 前三样合成观测量                                               | **亮温盒**（该时刻的 21cm 信号地图）                                                 |

> 记住这个顺序：**密度 → 晕 → 逐格辐射 → 电离与温度 → 信号**。每一环都在把"上一种形态的量"翻译成下一种形态的量。

### 0.3 三条流水线：同一台引擎，三种交付方式

> **代码位置**：`src/py21cmfast/drivers/coeval.py`、`src/py21cmfast/drivers/lightcone.py`、`src/py21cmfast/drivers/global_evolution.py`。

上面算出来的东西是**一批三维盒**。怎么把它交付出去，有三种方式（对外就是三个入口）：

|                         | 它回答的问题                         | 交付形态                               |
| :---------------------- | :----------------------------------- | :------------------------------------- |
| **E1 联合演化盒** | "某个宇宙时刻，整个三维宇宙长什么样" | 每个选定的时刻，一份完整的盒           |
| **E2 光锥**       | "观测者沿视线看过去会看到什么"       | 把不同时刻的切片按观测几何拼成的一张图 |
| **E3 全局演化**   | "整段历史的平均行为是什么"           | 每个时刻几个数（平均值），而不是盒     |

**关键事实**：这三条的物理计算**完全共用**——它们只是同一台引擎的三种收尾方式。所以本文先讲共用骨架（§2），再讲每条的差别（§3–§5）。

### 0.4 站位图

> **代码位置**：三个入口同上；C 侧对 Python 可见的入口全清单在 `src/py21cmfast/src/_functionprototypes_wrapper.h`。

```
① 参数 → ② 初始条件 → ③ 微扰场 → ④ 晕 → ⑤ 源项 → ⑥ 电离与热 → ⑦ 亮温
                       └──────── 共用骨架（§2）────────┘
                                                    ├─ 收尾 A：E1 联合演化盒（§3）
                                                    ├─ 收尾 B：E2 光锥（§4）
                                                    └─ 收尾 C：E3 全局演化（§5）
```

## §1 每一环的"上户口"：位置、动机、产物

这一节不讲任何算法，只把后面要反复用到的名词交代清楚：**它是什么、为什么有它、谁用它的输出**。名词按主链顺序出现，后面各节可以放心使用。

### 1.1 密度场（环节 ②③）

> **代码位置**：生成：`src/py21cmfast/src/InitialConditions.c`；演化到某时刻：`src/py21cmfast/src/PerturbedField.c`。字段名见 `src/py21cmfast/wrapper/outputs.py` 的 `InitialConditions`（`hires_density` / `lowres_density`）与 `PerturbedField`（`density`）。

**是什么**：一张三维网格，每格记录那里的物质比平均水平密多少（正数偏密、负数偏稀）。
**为什么需要**：宇宙的结构是"密的地方越来越密"长出来的，密度场就是这件事的起点与主变量。
**谁用**：微扰场（把它推到不同时刻）、晕（找塌缩区域）、亮温（信号的强弱也依赖密度）。

### 1.2 位移场与速度场（环节 ②③）

> **代码位置**：`src/py21cmfast/src/InitialConditions.c`（`compute_velocity_fields`、`compute_velocity_fields_2LPT`）与 `src/py21cmfast/src/PerturbedField.c`（`compute_perturbed_velocities`）。

**是什么**：物质不是待在原地，而是被引力拉着移动。"位移场"记录"要从哪挪到哪"，"速度场"记录"往哪个方向、多快"。位移场在初始条件阶段就一次算好（因为解的是一次性的引力问题），速度场在推到某个时刻时给出。
**为什么需要**：把物质从"初始位置"搬到"该时刻的位置"，才是那个时刻真实的密度分布。
**谁用**：微扰场（搬运质量）、晕（把晕的位置也挪到该时刻）、亮温（视线方向的速度会造成观测上的额外偏移，见 §4.3）。

### 1.3 红移（贯穿全链的时间标签）

> **代码位置**：红移序列：`src/py21cmfast/wrapper/inputs.py` 的 `node_redshifts` / `get_logspaced_redshifts`；推进：`src/py21cmfast/drivers/coeval.py` 的 `_redshift_loop_generator`。

**是什么**：光在传播途中被宇宙膨胀拉长的程度，也用作"距离/时间"的标签：红移越大 = 越早、越远。
**为什么需要**：整条链是**沿红移从高到低推进**的（从早到晚），每个红移上做一遍"中间那几步"。
**谁用**：所有环节；它也是 E2 把"频率"对应到"时间"的桥梁。

### 1.4 晕与质量函数（环节 ④）

> **代码位置**：`src/py21cmfast/src/HaloCatalog.c`、`src/py21cmfast/src/Stochasticity.c`（抽样）、`src/py21cmfast/src/hmf.c`（质量函数族与条件质量函数）。

**晕：是什么**：密度足够高的区域在引力下塌缩成的束缚结构。**为什么需要**：星系住在晕里，辐射来自星系，所以"哪里有多少晕"决定了"哪里有多少光"。
**质量函数：是什么**：一条统计规律，回答"给定质量尺度，单位体积里有多少个晕"。它还有一个"条件"版本，回答"如果某个区域比平均密一些/稀一些，那里应该多出/少掉多少晕"。
**为什么需要**：密度场本身不给出晕在哪、多重；质量函数是"密度 → 晕"这台翻译机的核心零件。
**谁用**：晕环节（决定要不要在这里放晕、放多重）、源项环节（把晕的属性按质量积分成格子上的量）。

### 1.5 标度关系（环节 ④→⑤）

> **代码位置**：`src/py21cmfast/src/scaling_relations.c`（`get_halo_stellarmass` / `get_halo_sfr` / `get_halo_metallicity` / `get_halo_xray`）。

**是什么**：把"晕有多重"翻译成"里面的星系产出多少东西"的一组规律——产出包括恒星质量、恒星形成率、电离光子数、X 射线。
**为什么需要**：质量函数只说"有多少晕"，不给出"这些晕发多少光"。
**谁用**：源项环节（逐晕赋值或在格点上积分）。

### 1.6 电离光子与逃逸分数（环节 ⑤）

> **代码位置**：逃逸分数：`src/py21cmfast/src/scaling_relations.c`；电离光子被积函数：`src/py21cmfast/src/hmf.c`。

**是什么**：能把氢原子电离的光子，主要由年轻恒星发出；**逃逸分数**是其中"成功离开星系、进入星系际介质"的那部分比例。
**为什么需要**：真正决定"宇宙被电离到什么程度"的，是逃逸出来的那部分光子。
**谁用**：电离环节。

### 1.7 X 射线与恒星形成率（环节 ⑤）

> **代码位置**：`src/py21cmfast/src/scaling_relations.c`（恒星形成率与 X 射线光度）；写进源项网格：`src/py21cmfast/src/HaloBox.c`；球壳滤波成 X 射线源箱：`src/py21cmfast/src/SpinTemperatureBox.c` 的 `UpdateXraySourceBox`。

**是什么**：恒星形成率是"这个星系每年造多少恒星"；X 射线是其中大质量恒星与双星系统的辐射，它能穿透较远、先把气体加热。
**为什么需要**：加热与电离的机制不同、作用范围不同，需要分开给。
**谁用**：热与自旋温度环节（X 射线负责加热与部分电离）。

### 1.8 自旋温度与中性分数（环节 ⑥）

> **代码位置**：`src/py21cmfast/src/IonisationBox.c`（中性分数）、`src/py21cmfast/src/SpinTemperatureBox.c`（自旋温度与温度演化）、`src/py21cmfast/src/thermochem.c`（率系数与温度公式）。

**中性分数：是什么**：某处还有多少比例的氢是中性的（没被电离）。
**自旋温度：是什么**：氢原子"自旋态"分布对应的一个等效温度；它决定 21cm 信号是被吸收还是发射、强还是弱。
**为什么需要**：观测到的 21cm 信号直接由这两个量（加上密度与气体温度）决定。
**谁用**：亮温环节。

### 1.9 亮温（环节 ⑦）

> **代码位置**：`src/py21cmfast/src/BrightnessTemperatureBox.c`；Python 入口 `src/py21cmfast/drivers/single_field.py` 的 `brightness_temperature`。

**是什么**：21cm 信号相对背景辐射（这里指弥漫全天的宇宙微波背景）的对比温度，就是最终那张"信号地图"。
**为什么需要**：它是观测量——前面所有环节的意义最终都要落到它上面。

### 1.10 本动速度与红移空间畸变（属于 E2 的额外一层）

> **代码位置**：速度：`src/py21cmfast/src/PerturbedField.c`、`src/py21cmfast/src/PerturbedHaloCatalog.c`；两项视线修正：`src/py21cmfast/rsds.py` 的 `apply_rsds` / `include_dvdr_in_tau21`。

**本动速度：是什么**：物质除了跟随宇宙整体膨胀之外的额外运动速度。
**为什么它会造成麻烦**：我们测到的红移 = 宇宙膨胀贡献 + 本动速度贡献。所以"观测到的红移"并不严格等于"真实的距离/时间"。
**红移空间畸变：是什么**：为了忠实反映"我们会观测到什么"，把本动速度对红移的影响显式加回去的那一步处理。它在 E2 里是可选的（见 §4.3）。

### 1.11 光锥（属于 E2 的核心概念）

> **代码位置**：`src/py21cmfast/drivers/lightcone.py`（`LightCone`、`generate_lightcone`）；观测几何：`src/py21cmfast/lightconers.py`（`Lightconer` / `RectilinearLightconer` / `AngularLightconer`）。

**是什么**：观测者看到的是**过去光锥**——离得越远的区域，我们看到的是它越早的样子。所以一张观测图上，**不同位置对应不同时刻**。
**为什么需要**：E1 给的是"某个时刻的整个宇宙"，那是理论上的切片；望远镜拿到的是"沿视线把不同时刻拼起来的一张图"。两者是不同的东西。

## §2 三条路共用的骨架

### 2.1 为什么要共用

> **代码位置**：共用件都定义在 `src/py21cmfast/drivers/coeval.py`：`_setup_ics_and_pfs_for_scrolling`（备料）与 `_redshift_loop_generator`（循环），三条路都调用它们。

因为"算一次宇宙怎么演化"这件事只有一种物理过程。三条路的差别只在**参数怎么给、循环之外多做了什么、结果怎么收**——所以骨架必须共用，否则同一份物理会被写三遍、还容易互相不一致。

### 2.2 骨架的第一段：准备（一次性）

> **代码位置**：`src/py21cmfast/drivers/coeval.py` 的 `_setup_ics_and_pfs_for_scrolling`（含 `evolve_halos`）。

**在做什么**：把所有"不随红移改变、或者可以一次算齐"的东西先备好。

- **初始条件**：如果调用方给了现成的，就直接复用；没给就现算。—— 这里涉及的"随机种子"就是决定那张随机密度场**具体长什么样**的那个数，所以"同一个种子得到同一套结果"。
- **把全部红移的微扰场一次算齐**：因为"把初始场推到某个时刻"这件事彼此独立，可以事先全算完，之后每个红移直接取用。
- **晕的演化也需要先备好**：晕是在不同红移上连续形成的，它的准备与前一步配套。

**为什么值得单独成为一段**：真正随红移重复的只有后半条链（辐射 → 电离 → 温度 → 信号）；把前半段一次做完，是三条路能共享、且能省掉重复计算的原因。

### 2.3 骨架的第二段：逐红移推进

> **代码位置**：`src/py21cmfast/drivers/coeval.py` 的 `_redshift_loop_generator`；它每一步调用的是 `src/py21cmfast/drivers/single_field.py` 里对应的单场入口。

**在做什么**：沿红移从高到低，每个红移上按**固定顺序**走一遍：

1. 取这个红移的**微扰场**（密度与速度，准备阶段已算好）；
2. 由密度场得到这一时刻的**晕**；
3. 把晕的统计与星系属性翻译成**逐格辐射**（源项）；
4. 由 X 射线等把气体**加热**、并把氢**电离**掉一部分（这两件事互相影响，一起解）；
5. 把密度、中性分数、自旋温度合成**亮温**。

**为什么必须逐红移、不能跳**：第 4 步里的电离与温度是**累积量**——这一时刻的状态取决于之前所有时刻累积的电离光子与热量。所以哪怕只想要最后一个时刻的结果，也必须从头一路推过来。

### 2.4 一个贯穿骨架的关键结构：上一时刻回喂下一时刻

> **代码位置**：传入方：`src/py21cmfast/drivers/coeval.py` 的 `_redshift_loop_generator`（把上一快照的字段作为 `previous_*` 传下去）；接收方：`src/py21cmfast/src/SpinTemperatureBox.c`、`src/py21cmfast/src/IonisationBox.c`、`src/py21cmfast/src/HaloBox.c`。

**是什么**：每个红移上算第 4 步时，都要用到**上一个红移**留下的两样东西：那时的电离状态与那时的温度状态。骨架会把它们从上一轮带进来。

**为什么需要**：因为上一条说的"累积"——电离与加热都是先有前因、后有后果的过程。这也是"必须按顺序推进"的更本质理由。

### 2.5 骨架的第三段：收尾（三条路在此分道）

> **代码位置**：`src/py21cmfast/drivers/coeval.py` 的 `generate_coeval`、`src/py21cmfast/drivers/lightcone.py` 的 `_run_lightcone_from_perturbed_fields`、`src/py21cmfast/drivers/global_evolution.py` 的 `run_global_evolution`。

**在做什么**：每个红移算完会得到一份"这一时刻的全部结果"，收尾就是决定怎么处置它们：

- **E1**：留一份完整的三维盒，最后交付一批盒（每个选定的时刻一份）；
- **E2**：不留下整个盒，而是从每个时刻的盒里按观测几何取点、拼进一张图；
- **E3**：把每个时刻的盒压成几个数（平均值），最后得到几条曲线。

### 2.6 换个看法：数据在哪些对象之间流动

> **代码位置**：产物类型定义在 `src/py21cmfast/wrapper/outputs.py`（`InitialConditions`、`PerturbedField`、`HaloCatalog`、`HaloBox`、`XraySourceBox`、`TsBox`、`IonizedBox`、`BrightnessTemp`）；快照容器 `Coeval` 在 `src/py21cmfast/drivers/coeval.py`；两种交付容器：`LightCone`（`drivers/lightcone.py`）、`GlobalEvolution`（`drivers/global_evolution.py`）。

§2.2–§2.5 是按**时间顺序**讲的，这里换成按**对象**看——谁把什么交给谁。全流程没有继承、没有多态：**类型只负责装数据，函数只负责搬数据**，所以数据流可以画成一张图（箭头 = 交出，不是修改）：

```
参数与选项（只读，沿线到处传）
        │
        ▼
  准备（一次性，§2.2）
        ├─ InitialConditions        复用调用方给的，或现算
        ├─ list[PerturbedField]     把全部红移一次算齐
        └─ list[HaloCatalog]        晕的演化
        │
        ▼
  逐红移推进（§2.3，每个红移一遍、顺序固定）
        HaloBox         ← 上一时刻的 IonizedBox、TsBox
        XraySourceBox   ← 迄今累积的全部源项网格
        TsBox           ← 上一时刻的 TsBox
        IonizedBox      ← 上一时刻的 IonizedBox、PerturbedField
        BrightnessTemp
        │
        ▼
      Coeval：该时刻的完整视图（把公共底座 InitialConditions 与上述各场挂在一起，
              构造时一次给全，之后不再改动）
        │
        ├─ E1 原样转交 ─────────────▶ 一批 Coeval（每个选定的时刻一份）
        ├─ E2 取点拼接 + 顺带折算均值 ▶ LightCone
        └─ E3 逐量折算平均值 ────────▶ GlobalEvolution
```

三件事值得单独记住：

1. **每一环交出的东西就是一种"盒类型"**：§0.2 表格"交出什么"那一列，在类型层面就是上面这些名字——一种盒只由对应环节产生、只被下游读。
2. **`Coeval` 是"某时刻的完整视图"，不是 E1 的私有类型**：三条路都经过它，区别只是 E1 直接把它交出去、E2 与 E3 拿它当原料（E2 取点拼接后顺带留下每个时刻的均值，E3 把每个时刻折算成几个数）。这也解释了为什么 E2、E3 的产物里也会有"逐时刻的均值"。
3. **唯一的"状态"是上一时刻那份快照**（§2.4）：`HaloBox`、`TsBox`、`IonizedBox` 都要读它，所以顺序不能乱——这也是 E3 虽然只用几个数，却仍然必须走同一条循环的原因。

## §3 E1 联合演化盒

### 3.1 为什么需要它

> **代码位置**：`src/py21cmfast/drivers/coeval.py`。

因为很多分析要的是"**同一个时刻的整个三维宇宙**"：比如算这一时刻的信号有多强的空间起伏、气泡长什么样、不同物理量之间怎么相关。这些问题的前提是"所有格点处于同一时刻"——把不同时刻的格点混在一起，物理上不成立。

### 3.2 它交出什么

> **代码位置**：快照对象：`src/py21cmfast/drivers/coeval.py` 的 `Coeval`；各字段本身来自 `src/py21cmfast/wrapper/outputs.py` 定义的输出结构。

一批盒，每个盒里装着该时刻的七件东西（对应主链第 ②–⑦ 环在该时刻的快照）：密度、速度、晕的信息、逐格辐射、中性分数、自旋温度、亮温。可以把它们理解为**同一台相机在不同时刻各拍的一张全景照片**。

### 3.3 它怎么工作（把骨架套进来）

> **代码位置**：`src/py21cmfast/drivers/coeval.py` 的 `generate_coeval` / `run_coeval`（后者只是把前者抽干）。

1. **准备**（§2.2）：初始条件 + 全部红移的微扰场一次备齐；
2. **逐红移推进**（§2.3）：每个红移走一遍五步，并用上一轮的"电离状态、温度状态"回喂（§2.4）；
3. **收尾**：把每个红移的结果各留一份完整盒，逐个交付。

**它与另外两条最大的不同**：它什么都不额外做——不切片、不取平均，因为"每个时刻本身"就是它的产品。

### 3.4 一个容易误解的点：选定的时刻会改变结果吗

> **代码位置**：输出红移与演化红移的区分：`src/py21cmfast/wrapper/inputs.py` 的 `node_redshifts`；合并逻辑：`src/py21cmfast/drivers/coeval.py` 的 `_get_required_redshifts_coeval`。

可以指定"要哪几个时刻的结果"，但**演化本身发生在一条固定的红移序列上**。也就是说：改"要哪几个输出"只影响交付哪些照片；而如果去改"演化序列本身"，那才会改变物理结果（因为累积过程的每一步都被改变了）。

## §4 E2 光锥

### 4.1 为什么需要它

> **代码位置**：`src/py21cmfast/drivers/lightcone.py`（光锥本体与拼接）与 `src/py21cmfast/lightconers.py`（观测几何的三种定义）。

因为**观测者看到的是过去光锥**（§1.11）：望远镜上的一张图，横轴是视线方向、纵轴是频率；**频率对应红移、红移对应时刻**——离得越远的部分，我们看到的是它越早的样子。所以 E1 的"某时刻的整个宇宙"并不是观测形态。

### 4.2 它交出什么

> **代码位置**：`src/py21cmfast/drivers/lightcone.py` 的 `LightCone`。

一张"观测形态"的图：把不同时刻的切片按观测几何拼在一起。它同时保留了每个时刻的平均值（作为副产品）。

### 4.3 它比 E1 多做的事

> **代码位置**：取点拼接：`src/py21cmfast/lightconers.py` 的 `make_lightcone_slices`；两项修正：`src/py21cmfast/rsds.py` 的 `apply_rsds` 与 `include_dvdr_in_tau21`。

1. **按观测几何取点并拼接**：光锥不是简单地"把盒叠起来"，而是沿视线按距离（也就是按红移）取采样点，把从一个时刻到下一个时刻之间的部分**插值**填上——因为一张连续的图上，两个时刻之间也有内容。
2. **视线方向的两项修正**（都属于 §1.10 那一类"本动速度惹的麻烦"，且都是可选的）：
   - **红移空间畸变**：把本动速度对"观测到的红移"的影响显式加回去，使图更接近真实观测；
   - **沿视线的速度变化对"气体遮挡程度"的修正**：先说清这里涉及的第二个名词——**光学深度**，它是"这段气体把背景光挡掉多少"的量度（21cm 信号正是由气体对背景光的吸收/发射形成的）。而气体沿视线的**速度是否有变化**会影响这个遮挡程度，所以要单独修一次（"速度梯度"就是指沿视线的速度变化）。

### 4.4 它怎么工作（把骨架套进来）

> **代码位置**：`src/py21cmfast/drivers/lightcone.py` 的 `_run_lightcone_from_perturbed_fields`。

**准备**与**逐红移推进**完全沿用骨架（§2）；差别在收尾：每个红移算完后不保留整盒，而是立刻把该时刻的采样点写进那张图；循环结束后再做上面那两项可选修正。

## §5 E3 全局演化

### 5.1 为什么需要它

> **代码位置**：`src/py21cmfast/drivers/global_evolution.py`。

因为有一类问题只要**平均值的历史**：整体上"宇宙什么时候被电离掉一半"、平均信号随时间怎么走、气体整体上被加热到什么程度。要这些量时，算出整个三维宇宙的每个细节是多余的。

### 5.2 它交出什么

> **代码位置**：`src/py21cmfast/drivers/global_evolution.py` 的 `GlobalEvolution` 与其 `quantities` 字段。

每个时刻几个数：平均中性分数、平均自旋温度与气体温度、平均亮温等——**曲线而不是地图**。

### 5.3 一个必须说清的点：平均值是从哪来的

> **代码位置**：0-D 电离盒：`src/py21cmfast/drivers/global_evolution.py` 的 `compute_global_reionization_at_z`；平均电离光子产出：`src/py21cmfast/wrapper/cfuncs.py` 的 `evaluate_Nion_z`；平均恒星形成率密度与全局属性：`src/py21cmfast/src/SpinTemperatureBox.c` 的 `EvaluateSFRD` 一族与 `global_reion_properties`；闭合项：`src/py21cmfast/wrapper/inputs.py` 的 `CLUMPING_FACTOR`（用法在 `src/py21cmfast/src/SpinTemperatureBox.c`）。

这是最容易误解的地方。平均值**不是**"先把三维场算出来再平均掉"，而是**直接算出来的**：

- 有些平均值可以由**统计规律直接给出**（例如"平均产生多少电离光子"可以由质量函数与标度关系积分得到，不需要真的在哪里放晕）；
- 有些量**无法**由平均值自身决定（典型是复合：复合速率取决于"电离程度有多不均匀"，而不只是平均电离程度），只能用**参数化的假设**补上。

所以 E3 的"一格代表整个宇宙"是这样成立的：**它把方程里每一项的平均值用解析办法算出来，再用假设补上少数无法解析得到的项**。

### 5.4 它的代价

> **代码位置**：被放弃的模块正是为空间场与气泡服务的那两处：`src/py21cmfast/src/IonisationBox.c` 的游程集路径与 `src/py21cmfast/src/photoncons.c`；补不回来的项见 `CLUMPING_FACTOR` 的用法处。

放弃空间信息是有代价的：空间起伏、电离的不均匀、气泡形态一概没有；而那些"补不回来"的项（比如上一条说的复合）一旦假设不准，平均值就会系统性偏。

因此有一条很自然的用法：**E1 的盒平均可以当作 E3 的对照基准**——两者不一致时，先怀疑的是"参数化假设"，而不是 E1。

### 5.5 它怎么工作（把骨架套进来）

> **代码位置**：`src/py21cmfast/drivers/global_evolution.py` 的 `run_global_evolution`（含把参数改成「只剩一格」版本的那一步）。

准备与逐红移推进沿用骨架，但**参数被压成"只有一个格"的版本**：因为没有空间结构，位移、气泡这些步骤失去意义；收尾则是把每个时刻的盒直接折算成平均值，逐时刻写进曲线。

## §6 三条并排对照

> **代码位置**：三条的落点见 §3–§5 各节；共用的备料与循环都在 `src/py21cmfast/drivers/coeval.py`。

|                  | E1 联合演化盒          | E2 光锥                        | E3 全局演化              |
| :--------------- | :--------------------- | :----------------------------- | :----------------------- |
| 要什么形态       | 某时刻的整个三维宇宙   | 观测者沿视线看到的一张图       | 平均值的曲线             |
| 参数怎么给       | 原样                   | 原样，另加观测几何与那两项修正 | 先压成"只剩一格"的版本   |
| 共用骨架         | ✅ 准备 + 逐红移推进   | ✅ 同左                        | ✅ 同左                  |
| 循环之外多做什么 | 无                     | 取点拼接 + 可选的两项视线修正  | 无（循环本身也不一样了） |
| 收尾             | 每个时刻留一份完整盒   | 把切片拼成图                   | 把盒折算成平均值         |
| 主要用途         | 空间统计、形态、相关性 | 与观测直接比较                 | 快速扫参数、看整体历史   |

## §7 一句话总结

> **代码位置**：骨架：`src/py21cmfast/drivers/coeval.py`；三种收尾：`coeval.py` / `lightcone.py` / `global_evolution.py`（均在 `src/py21cmfast/drivers/`）。

**三条路是同一台引擎的三种交付方式**：E1 交每个时刻的完整宇宙，E2 交观测者看到的那张图，E3 交平均值的历史；而在它们内部，走的都是同一条链——**密度 → 晕 → 逐格辐射 → 电离与温度 → 信号**，并且必须沿红移从高到低一路推过去，因为后面的状态依赖前面的累积。
