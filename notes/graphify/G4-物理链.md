### 1.1 本层的三条硬规矩

1. **一级只放天体物理过程与层**：块名一律写成「这一步在物理上算什么」（`气体热与自旋温度`、`亮温与观测`），不放代码阶段名、不放函数名、**不带编号**。
2. **一个块 = 一个代码模块**：块的身份由真源逐块声明的 `codeAnchor` 给出——一个 `.c` 文件 + 一个 `Compute*` 入口 + 一个输出盒子（层只声明文件：`Constants.c`）。这条是可证伪的：自检打开那个文件核对函数名、结构名与常量行。
3. **能被推出来的才进子图**：过程块可进入；层不可进入（它的成员是常数，没有块内边可看）；代码实现（`质量函数的算法`、`源项的实现`）是**块的成员**、标签里注明「（子图）」，工程项只出现在块内、呈暗色。

### 2.1.1 逐块读法

#### 常数与网格

- **作用与意义**：最底层——整场仿真里不随红移变的量与网格尺寸一次定死；`T_γ(z) = T_CMB · (1+z)` 既是气体温度的绝热基准，也是自旋温度与 Ly-α 耦合的参照温度。
- **成员**：`T_γ`（CMB 温度）。**它是层，不是过程**：成员是常量，没有块内边。
- **接口边**：入 0 条；出 2 条 → 气体热与自旋温度、亮温与观测，各一条 `T_γ`。
- **代码锚**：`Constants.c` · `PhysicalConstants`（`.T_cmb = 2.7255`，`:25`）+ `SimulationOptions`（`HII_DIM` / `DIM` / `BOX_LEN` / `Z_HEAT_MAX`）。**进入**：不可。

#### 宇宙学背景与物质功率谱

- **作用与意义**：线性功率谱 `T(k)` 与 σ(R) / dσ²/dM 表；宇宙学参数先整理成常数，再逐模求值，供质量函数插值。
- **成员**：`T(k)`（物质转移函数）→ σ(R) / Δ²(k)（物质功率谱与 σ(R)）。
- **接口边**：入 0 条；出 2 条 → 初始条件、晕目录与质量函数，各一条 `σ(R) / Δ²(k)`。
- **块内边**：1 条 `T(k) → σ(R) / Δ²(k)`。**代码锚**：`cosmology.c` · `init_ps` · `CosmoTables`。**进入**：可。

#### 初始条件

- **作用与意义**：产出线性密度场、位移场与 `lowres_vcb`（相对速度场）；它同时是三条反馈里"相对速度"那一条的源头。
- **成员**：`δ_i(x)`（线性初始密度场）→ `v_1LPT(x)`、`v_2LPT(x)`（一阶 / 二阶 LPT 速度场），以及 `v_cb`（重子-暗物质相对速度）。
- **接口边**：入 1 条 ← 宇宙学背景与物质功率谱 `σ(R) / Δ²(k)`；出 5 条 → 引力扰动、气体热与自旋温度、电离场（各一条 `v_cb`）、网格化源项（`v_cb`）、晕目录与质量函数（`δ_i(x)`：它交给晕查找器的是**线性**初始密度场，不是 `δ(x)`，见 §七 第 10 条）。
- **块内边**：2 条 `δ_i(x) → v_1LPT(x)`、`δ_i(x) → v_2LPT(x)`。**代码锚**：`InitialConditions.c` · `ComputeInitialConditions` · `InitialConditions`。**进入**：可。

#### 引力扰动

- **作用与意义**：高分辨→低分辨的一阶拉格朗日位移重映射（辅助函数在 `map_mass.c`）；下游四块都拿它当参数。
- **成员**：`δ(x)`（扰动密度场）→ `v(x)`（低分辨速度场）。
- **接口边**：入 1 条 ← 初始条件 `v_cb`；出 3 条 → 气体热与自旋温度、电离场、亮温与观测，各一条 `δ(x)`。**不出到晕查找器**：`ComputeHaloCatalog` 的形参只有 `InitialConditions *boxes`，没有 `PerturbedField`（见 §七 第 10 条）。
- **块内边**：1 条 `δ(x) → v(x)`。**代码锚**：`PerturbedField.c` · `ComputePerturbedField` · `PerturbedField`。**进入**：可。

#### 晕目录与质量函数

- **作用与意义**：Eq.1 的被积函数 `dn/dM`、Eq.2 的 `M_min(z)`，以及"把 `dn/dM` 算出来"的算法（算法本身进子图）。旧稿把它切成「质量函数」与「质量阈值」两块，代码里是同一个 `ComputeHaloCatalog` + `hmf.c` + `Stochasticity.c`。
- **成员**：`T_vir^min` → `M_min(z)`（Eq.2）、`质量函数的算法` → `dn/dM(M,z)`（Eq.1 的被积函数）。
- **接口边**：入 2 条 ← 宇宙学背景与物质功率谱、初始条件；出 2 条 → 晕到星系属性（`dn/dM(M,z)`、`M_min(z)`）、网格化源项（`dn/dM(M,z)`）。
- **块内边**：2 条 `T_vir^min → M_min(z)`、`质量函数的算法 → dn/dM(M,z)`。**代码锚**：`HaloCatalog.c` · `ComputeHaloCatalog` · `HaloCatalog`。**进入**：可。

#### 晕到星系属性

- **作用与意义**：只算**每个晕**的属性：标度关系把晕属性换成星系属性（旋钮 `F_STAR10` / `ALPHA_STAR` / `L_X` / `F_ESC10`），并给出 UV 光度函数 `φ(M_1500,z)`；网格化留给「网格化源项」。
- **成员**：`f*` → `标度关系(M_h)` → `ρ̇*(z)`；`φ(M_1500,z)`；`L_X`（X 射线光度，每单位恒星形成率）。
- **接口边**：入 1 条 ← 晕目录与质量函数；出 2 条 → 网格化源项（`标度关系(M_h)`、`f*`、`ρ̇*(z)`）、气体热与自旋温度（`L_X`、`ρ̇*(z)`）。
- **块内边**：4 条 `f* → 标度关系(M_h)`、`标度关系(M_h) → ρ̇*(z)`、`f* → φ(M_1500,z)`、`ρ̇*(z) → φ(M_1500,z)`。**代码锚**：`PerturbedHaloCatalog.c` · `ComputePerturbedHaloCatalog` · `PerturbedHaloCatalog`。**进入**：可。

#### 网格化源项

- **作用与意义**：把每个晕的属性摊到网格上，产出 `halo_sfr` / `nion` / `halo_xray` / `whalo_sfr` 四张网格；它是唯一一个把全部源项旋钮收进签名的步。**两条回流边都回到这一块**——它在签名里同时收 `previous_spin_temp` 与 `previous_ionize_box`。
- **成员**：`ζ` → `Ṅ_ion(z)`（Eq.4）；`源项的实现`（条件积分与铺场算法）。
- **接口边**：入 3 条 ← 晕到星系属性、晕目录与质量函数、初始条件；出 2 条 → 电离场（`Ṅ_ion(z)`）、X 射线源的历史卷积（`源项的实现`）；**回流入 2 条** ← 气体热与自旋温度、电离场。

### 3.6 代码锚：块与代码的同构关系

每个过程块的真源条目里都有一条 `codeAnchor`（`{file, function, struct}`），层给 `{kind: "files", files}`。它不是装饰：

- **属性页的「源码」标签页**铺开的落点就来自它——一个量算在哪个文件、哪段行，逐条可点即开；界面上只给不带目录的文件名（`SpinTemperatureBox.c`），完整路径退到 `title`。
- **自检打开那个文件**逐条核对函数名与结构名，所以"一个块 = 一个代码模块"这句话是可证伪的：改错文件名或函数名，`check:chain` 立刻失败并指名。
- **两个块可以共用同一个文件**：「X 射线源的历史卷积」与「气体热与自旋温度」都在 `SpinTemperatureBox.c`，靠函数名分开（`UpdateXraySourceBox` / `ComputeTsBox`）——自检按「文件 + 函数」核对，不按文件名去重。

- **选中参数时，选中落在"第一个块"上**（不再落在藏在块里的成员上，避免"选中了却看不见"）：右侧栏随之给过程块的属性页；左栏脚上那份"作用于 …"清单里每一项都可点，点它就进那个块并选中那个量。**点画布空白 = 把本页点亮整体熄灭**——红点全灭、词条行不再高亮、脚上区收起，并清掉选中；从过程面、检索命中与点红点来的点亮走同一条熄灭口径（只熄本页，画布页的勾选与选中不受影响）。这一区**最高占左栏一半**（超出在区内滚动）——作用于十几个量的参数不再把上面的词条清单顶出视野；区里只有参数名、代码类徽标与两份可点清单，「作用于 N 个量 / 落在哪几个块」在名字那一行的悬停提示里读；一个量都不直接作用时分两种：**开关类**在「作用于 无（它不改量的值，改的是走哪一支）」之外多列一行「门控」，把门控边两端的量摆出来（点了同样定位过去——`fstar -> scaling_relations` 这条边挂着它们）；**真没有落点**的才写原因，原因按数据分两种：`代码里没有它`（`inCode` 为假）/ `链上没有量落在读到它的那段代码上`。同一口径也写在检索说明里（开关写成"不改量的值，为真时改走 N 个量那支"＋"门控 `f* → 标度关系(M_h)`"，边两端只取符号那一半），且它命中后定位到那条边上的量。

- **两个"驱动"不是一个东西**（容易读岔，先钉死）：生成物**顶层**的 `drivers` 是 **5 个物理驱动量**——`f*`、`ζ`、`T_vir^min`、`L_X`、`k`（带论文出处 `eq` / `reviewSection` / 取值范围 `rangeText`；`stats.drivers = 5` 指的就是它）；参数分组里的 **`params.drivers` 是 8 个代码参数**——`ALPHA_STAR`、`F_STAR10`、`F_ESC10`、`HII_EFF_FACTOR`、`POP2_ION`、`M_TURN`、`L_X`、`ION_Tvir_MIN`。两组只有 `L_X` 同名，其余是"一个物理量 ↔ 若干代码参数"的对应关系（写在驱动量的 `codeNames` 里）。
- **效应开关挂在边上**：`effects` 组带 `gatesEdges`（它门控的边 id）与 `basis`（为什么挂这条边，含代码读点）——例如 `USE_TS_FLUCT` 门控 `ts→dtb`，`PHOTON_CONS_TYPE` / `USE_MINI_HALOS` 挂在源项相关的边上。虚线（箭头上的虚线框）= 这条依赖只在某些配置下成立。
